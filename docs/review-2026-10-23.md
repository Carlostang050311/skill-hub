# skill-hub 代码审查与后续路线（2026-10-23）

## 结论

skill-hub 已经超过功能原型阶段：扫描、推荐、分发、评测、修复预览、备份恢复、Web、CLI、MCP 和 GitHub 来源管理都能在本地工作。但它目前还不是一个可以无条件运行陌生 Skill、并长期保存可信质量结论的平台。

下一阶段的主线应从“继续增加功能”切换为“建立可信的本地控制面”：

1. 统一库存、来源、副本、版本和扫描运行的领域模型。
2. 让 CLI、Web、MCP 读取同一个持久化库存，并共享契约与错误结构。
3. 把评测结果绑定到可复现输入，记录重复运行、成本、延迟、评审和证据。
4. 在执行级评测前建立明确的信任等级和安全边界。
5. 再用推荐反馈和版本趋势形成长期闭环。

## 如果从零开发

第一版的目标用户应限定为“管理多个 Agent 客户端 Skill 的个人开发者和小团队”。核心承诺只有一句：**帮助用户发现适用 Skill，确认来源可信，评估它是否有效，并安全地同步和升级。**

第一版不同时承担公共 marketplace、通用模型评测平台、全能 Agent 沙箱和团队协作系统。先把本地库存、可复现评测、受控同步和清晰诊断做可靠，再扩展生态和自动化。

从零开始的最小可交付闭环是：

```text
配置 roots → 扫描并生成 snapshot → 推荐/查看 → 受控评测
       ↑                                ↓
       └────── 反馈、修复、重新评测、版本趋势 ──────┘
```

## 本轮验证基线

本轮在 Windows 工作区重新运行：

- `npm test`：31 个测试文件、158 个用例通过。
- `npm run build`：core、CLI、eval、MCP、Web 生产构建通过。
- 真实本机只读扫描：375 条有效记录、5 个扫描根、3 个解析失败。解析失败来自 ZCode 插件缓存中已有的第三方 `browser-use` YAML 文件，未修改原文件。
- 本轮没有运行真实外部模型评测，也没有重新执行 Edge/Playwright 全流程；2026-10-08 的浏览器证据仍属于历史证据，不能直接当作本轮验证。

## 代码审查发现

### P0：执行级评测没有操作系统安全隔离

证据：`apps/eval/src/exec.ts:41-55` 明确把沙箱定义为输出目录约束；`apps/eval/src/artifacts.ts:55-66` 直接启动 Node 子进程。

陌生 Skill 或其生成的程序可以读取工作目录之外的文件、访问网络、读取环境信息、启动其他进程或消耗过多资源。当前实现只适合明确受信任的本地 Skill，不适合直接执行 GitHub、插件缓存或未知来源内容。

处理顺序：默认 `trusted-only`；增加 `trust_level` 和执行确认；再按 Windows 能力落地 worker 进程、网络策略、临时用户目录、超时/内存/磁盘配额和审计日志。没有真正隔离前，产品文案必须持续明确这一边界。

### P1：备份交换存在并发竞态和跨盘孤儿目录

证据：`packages/core/src/backups.ts:39-40` 在计算目标指纹后才进行目录交换，另一进程可以在窗口内修改目标；`packages/core/src/backups.ts:53-57` 的 `EXDEV` 分支会留下 `.skillhub-original-*` 临时目录，成功路径没有统一清理。

处理顺序：同一目标使用锁；交换前后再次校验；所有 stage、original 和 pending 目录由 `finally` 清理或显式登记为可恢复现场；补充跨盘和并发回归测试。

### P1：破坏性删除没有确认、备份或内容指纹保护

证据：`packages/core/src/distribute.ts:154-155` 的卸载直接递归删除；`packages/core/src/distribute.ts:218-219` 的打包会先删除同名输出目录。若输出目录与来源目录重合，`pack` 可能先删除源 Skill 再复制。

处理顺序：禁止来源与输出路径重叠；改为临时目录加原子替换；删除前要求显式确认或先生成备份；卸载必须按目标来源解析副本并校验预期指纹。CLI、Web 和库函数要使用同一安全策略。

### P1：CLI 的 `--home` 没有贯穿 GitHub 来源和分发路径

证据：`packages/cli/src/cli.ts:334`、`:362`、`:446`、`:456`、`:599`、`:611` 使用固定的 `GITHUB_CACHE_ROOT`、`ORIGINS_FILE` 或默认用户目录，而不是命令传入的自定义 home。

结果是扫描看到的是隔离 home，安装、来源登记和远程更新却写入真实用户目录，可能造成“命令成功但库存不一致”。

处理顺序：统一从 `home` 派生状态路径、缓存路径、来源注册表和目标目录；为 `github-install`、`adopt`、`origins`、`outdated-remote` 增加隔离 home 回归测试。

### P1：评测与 Web 数据库连接没有统一关闭

证据：`apps/web/lib/evaldb.ts:17-19`、`:67-73` 打开数据库后未关闭；`apps/eval/src/cli.ts` 的 ingest/report 路径也存在同类使用方式。

长驻 Web 进程和 Windows 文件锁环境下，连接泄漏会导致数据库无法移动、备份或升级。所有 Repository 调用都应采用 `try/finally`，并由存储层统一管理连接生命周期。

### P1：来源注册表模型和损坏恢复不足

证据：`packages/core/src/github.ts:128-147` 以 Skill 名称作为唯一键，同名 Skill 在不同来源或目标目录会互相覆盖；JSON 损坏时 `loadOrigins` 静默返回空对象，后续写入可能覆盖用户原有登记。

处理顺序：以 `origin + revision + target` 建模；损坏文件进入 recovery error 并拒绝覆盖；保存采用临时文件、校验、原子 rename 和备份。

### P2：状态写入、扫描诊断和契约不统一

- `apps/eval/src/runner.ts`、`apps/eval/src/cli.ts`、`apps/web/lib/workbench.ts` 和 `packages/core/src/github.ts` 各自直接写 JSON，没有统一锁、事务、格式版本和迁移。
- `packages/core/src/scanner.ts` 对目录读取、快照和解析异常缺少结构化原因，根报告只能看到失败数量和路径。
- CLI、Web、MCP 分别做参数解析和类型断言，没有共享请求/响应 DTO 与错误码。
- MCP 每次调用都全量扫描，扫描后再读正文；文件在两步之间消失时会产生未处理错误。
- `snapshotDirectory` 和 `hashDir` 只保存 16 位摘要；库存列表可以使用短指纹，但来源、更新和评测绑定应保留完整 SHA-256。
- 扫描和 GitHub 克隆没有文件数、单文件大小和总大小配额，面对大型或恶意仓库时存在资源耗尽风险。

## 测试审查

现有单元测试覆盖面不错，已经覆盖解析、指纹、推荐、评分、作业恢复、产物检查、备份修复和 MCP stdio。但以下测试仍是缺口：

- 跨盘 `EXDEV` 备份成功、失败和孤儿目录清理。
- 两个进程同时 install/restore/recordOrigin 的锁和冲突行为。
- `pack` 源目录与输出目录重合、已有自定义文件、取消和恢复。
- uninstall 的目标来源选择、预期指纹和备份保护。
- 自定义 `--home` 下的 GitHub 安装、来源登记、远程更新和目标目录。
- 损坏 `origins.json`、任务 JSON、报告 `raw_json` 的隔离恢复和不覆盖原则。
- 评测执行越权、符号链接 TOCTOU、网络/进程/资源限制。
- Web route 的非法 JSON、超大 body、错误来源、错误码和并发写入。
- MCP 中扫描后文件消失、权限变化和单个 Skill 读取失败。
- 场景目录同时包含 `scenarios` 与 `scenarios-auto` 的重复 Skill 和重复作业 ID。

测试策略应分为四层：领域纯函数、存储/迁移、应用用例、真实 CLI/Web/MCP 验收。每层都要有独立夹具和可复现的临时 home，不把真实用户目录写入测试。

## 技术选型审查

| 选择 | 判断 | 后续动作 |
| --- | --- | --- |
| TypeScript monorepo | 保留。core、CLI、Web、MCP 和 eval 共享领域类型，适合本地工具的单仓库演进。 | 把共享对象移到 domain/contracts，入口只做适配。 |
| Next.js 15 | 保留。当前本地仪表盘和 API 已经能满足需求。 | 不继续把领域逻辑放进 route；统一调用 application 层。 |
| Commander | 保留。命令数量和交互复杂度仍在可控范围。 | 参数校验迁移到共享 schema，统一 JSON 输出和错误码。 |
| Vitest + Playwright | 保留。单元、协议和浏览器验收分层清晰。 | 增加并发、迁移、安全执行和真实失败场景。 |
| YAML scenario | 保留。适合人工编写、审阅和版本控制。 | 统一 frontmatter/scenario parser，保留行列诊断和 dataset version。 |
| `node:sqlite` | 短期可保留，但不应直接散落在 Web/eval 业务代码。它要求较新的 Node，并且 API 仍有实验性变化。 | 新增 storage adapter、启动版本诊断、schema migrations；未来可切换成熟驱动而不改领域层。根 `package.json` 还应声明 Node engines。 |
| JSON/JSONL 状态文件 | 适合导出、交换和临时作业，不适合核心状态。 | 核心状态进入 SQLite；JSON 必须带 schema version、校验和原子写入。 |
| 词法推荐 | 现阶段保留，简单、可解释、离线可用。 | 先加入采用/拒绝反馈和离线命中率，再决定是否引入语义检索。 |

从零开发时，最重要的技术决策不是换框架，而是先把 `domain → application → storage → adapters → CLI/Web/MCP` 分层。这样可以在不重写产品入口的情况下替换 SQLite 驱动、评测 provider 和执行隔离方案。

## 明确暂不做

- 不先做云端账号、公共 marketplace 或团队协作权限。
- 不先引入 embedding、向量数据库或复杂推荐模型。
- 不把 Node `node:sqlite` 直接散落在业务代码；短期可保留，但必须封装在 storage adapter 后面。
- 不把工作目录约束称为操作系统沙箱。
- 不把历史榜单、协议夹具分数或代码存在当成真实模型质量证明。

## 下一步实现切片

下一轮应只实现一个可验收切片：

> `inventory.db` + `scan_runs` + Repository + shared contracts，让 CLI/Web/MCP 共享一次扫描快照。

验收标准：

1. 同一 `scanRunId` 可被三个入口查询。
2. 增量扫描只重算发生变化的文件。
3. 解析失败保留原文件并写入结构化 diagnostics。
4. 两个并发写入不会互相覆盖或产生半写文件。
5. 现有 `npm test`、`npm run build` 和真实 CLI/Web 验收继续通过。
